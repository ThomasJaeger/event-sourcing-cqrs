# 0055. Command and workflow recovery

## Status

Accepted (September 2026). Amends ADR 0016 and the earlier relational outbox and compensation ordering decisions. This records implementation behavior; the manuscript is unchanged.

## Decision

Keyed aggregate writes include `idempotency_key` in event metadata, atomically with the effects. Repositories check that receipt before deciding and before appending; optimistic concurrency closes the race between the check and append. A conflicting append checks for the receipt again. Snapshot loads also check receipts preceding the snapshot. The pipeline converts an already-committed result into no-op success and repairs the optional command cache. A cache write after dispatch cannot, by itself, protect against repeated effects after a crash.

Receipts are scoped to an aggregate stream (including tenant); originators must retain the same target and payload when retrying a logical command. Keys are exact, case-sensitive strings limited to 200 UTF-8 bytes, the narrowest shipped cache schema. Unkeyed commands remain outside this guarantee. These guarantees apply to aggregate writes through the registered repositories, not arbitrary external side effects. Payment provider integration would need provider-side idempotency too. PostgreSQL and SQL Server probe metadata directly; the other adapters use the event-store contract's stream scan. Long-lived streams may warrant an indexed receipt implementation in those adapters.

Relational outbox processors use one ordered dispatch lane per database, protected by a transaction-scoped database lock. A failed event ends the batch. Backoff and quarantine block later positions, including in other workers. Projections use global checkpoints, so allowing later events through would make an earlier retry disappear behind the checkpoint. This favors correctness over throughput and availability during a poison event. A checkpoint row is created and locked in the same transaction as the projection mutation, including first delivery, preventing concurrent double increments.

API commands, fulfillment event handlers, and timeout commands coordinate by tenant and order through `IWorkflowLock`. All hosts, including hosts using SQL Server, KurrentDB, or DynamoDB for events, must connect to the same PostgreSQL read-model database for this coordination. The lock is reentrant for nested commands in one execution flow; it is not stored business state. Do not bypass the command pipeline for production writes. The database lock depends on a live connection and is not an external-system fencing token.

Customer order mutations check ownership as well as role permissions. Cancellation records the authenticated actor rather than trusting the payload. Cancellation checks the authoritative shipment under the order lock; authorization, scheduling, and dispatch reject cancelled orders. Timeout handlers inspect the committed payment or shipment so delayed event delivery cannot be mistaken for failure.

`OrderCancelled` triggers fulfillment compensation. Cancellation recovers inventory reservations committed before the fan-out outcome save, and persists the recovered set before releasing anything. Compensation first cancels the order to prevent further fulfillment, then releases inventory and voids payment. A failed step propagates to retry/quarantine; the process manager saves its terminal state only after every required command succeeds. Completion similarly propagates a rejected `MarkOrderCompleted`. Durable step keys allow earlier successful steps to be retried safely.

## Deployment and recovery

1. Stop old API and worker instances before upgrading. Old binaries do not honor the new coordination locks or receipt rules; mixed-version execution does not provide these guarantees. Deploy all instances with the same read-model connection target, then resume traffic and workers.
2. Inspect existing outbox quarantine rows before resuming workers: they now block later events. Alert on a nonempty quarantine and on pending outbox age. A growing backlog with no progress requires intervention, not checkpoint advancement.
3. Repair the failing consumer or its underlying dependency before retrying a quarantined event. Keep an audit copy of the quarantine record and error. Stop workers while performing manual recovery.
4. Requeue the earliest quarantined record in one database transaction: join it to `event_store.events` by `event_id` to recover `global_position`; insert it into `event_store.outbox` with its **original `outbox_id`**, event id, stored event type/version, payload, metadata and occurrence time; set `sent_utc`, `next_attempt_at`, and `last_error` to null and `attempt_count` to zero. PostgreSQL identity insertion requires `OVERRIDING SYSTEM VALUE`; SQL Server requires `SET IDENTITY_INSERT event_store.outbox ON` for that session, followed by `OFF`. Delete the selected quarantine row only after exactly one outbox row has been inserted, then commit. Roll back on a missing source event or any duplicate/conflicting identity. Do not allocate a new outbox id or advance projection checkpoints to bypass the event.
5. Restart workers and verify that the recovered event and subsequent positions complete. Repeat for additional quarantine rows. Replays may redeliver events to consumers that succeeded before another consumer failed; checkpoint locks and command receipts make that expected.
6. If older software already skipped events while advancing checkpoints, rebuild the affected read models from the event log using the existing replay procedure. The new ordering cannot repair previously skipped state by itself. Events written before this upgrade have no durable command receipt; preserve existing idempotency cache entries and reconcile ambiguous historical retries before resubmitting them.

The repository's database-backed regressions cover ordered retry/quarantine, checkpoint overlap, workflow lock serialization and release, cancellation before delayed dispatch notification, and receipt round trips on all four event-store adapters. Application and process-manager tests cover missing receipt caches, snapshot-hidden receipts, ownership, actor identity, failed compensation/completion, and partially persisted reservation fan-out.
