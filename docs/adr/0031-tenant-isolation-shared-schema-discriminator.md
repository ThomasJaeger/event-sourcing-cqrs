# 0031. Tenant Isolation by a Shared-Schema Discriminator

## Status

Accepted (June 2026). The parent decision ADR 0029 and ADR 0030 forward-referenced; recorded now that the foundation through P10.4 has landed. The read-isolation enforcement mechanism, left open at acceptance, is decided and recorded below as of P10.5. The projection-side tenant tagging and the tenant-scoped SKU keys, owed to P10.6 at acceptance, have landed and are recorded below as of P10.6.

## Context

Multi-tenancy ships in v1 (PLAN.md's amended scope). The isolation model is a shared-schema discriminator: one database, one schema, every tenant's data in the same tables, separated by a `tenant_id` discriminator rather than by a database or a schema per tenant. The tenant appears at more sites than any other identifier in the system: a `tenant_id` column on fourteen of the sixteen read-model tables, the two exceptions and their reasons recorded in migration 0017's header, and an indexed one on the events table, a tenant component in the stream id, the tenant on the runtime principal, and the tenant in event metadata.

A shared-schema discriminator trades isolation strength for operational simplicity. The cost is that isolation is a predicate, not a boundary the storage engine enforces: a read that omits the tenant predicate returns another tenant's rows. A one-line omission is a cross-tenant read, a security incident rather than an ordinary defect. The model therefore cannot rest on per-query discipline. It depends on read isolation enforced by infrastructure and on cross-tenant coverage that is structural rather than reviewer-dependent.

## Decision

The isolation model is the shared-schema discriminator. The tenant is a typed `TenantId` (ADR 0029), an isolation dimension the type system keeps distinct from every other identifier, so a structurally invalid tenant cannot reach a discriminator predicate.

The following have landed and are settled:

- The tenant in event metadata as a typed `TenantId`, and the events-table `tenant_id` column derived from metadata by a STORED generated column, with the corpus migrated bi-format-additively and no historical fact rewritten (ADR 0030).
- The tenant component in the stream id, tenant-after-prefix so prefix-family routing is unaffected, with `Parse` tolerating the legacy two-segment default-tenant form (ADR 0011 as amended, ADR 0030).
- The current-tenant accessor. `ICurrentTenantAccessor` lives in `Domain.Abstractions`, async-local-backed by `AsyncLocalCurrentTenantAccessor` in `Application/Context`, and is the single source of the current tenant on an async flow. It is read where the event tenant and the stream id are constructed (P10.4). It is set from the principal at the HTTP edge and from the causing event's metadata on the caused-command path. P10.5 adds the read-model `tenant_id` columns and reads the accessor at the query-side set-point and the subscription-authorization set-point to enforce read isolation, as recorded below. The projection worker-edge set-point landed at P10.6: the projection write path now resolves the event's tenant from the accessor, as recorded below. The outbox worker-edge set-point and the process-manager stream-identity tenant have since landed: the in-process dispatcher sets the tenant from event metadata around the projection and process-manager loops, and the process-manager propagation slice tenanted the loop at the accessor and tenant-formed the stream id, so those worker paths resolve their own tenant rather than the default.

The accessor's placement follows the consumer-set-asymmetry rationale ADR 0026 records: a port the engine-agnostic repositories and the later read-isolation path depend on lives in `Domain.Abstractions`, below `Application`, while the principal factory that populates it from a read model stays in `Application`, the same split ADR 0028 made for `CurrentRolesPrincipalFactory`. The port is low because consumers below `Application` reach it; the factory is in `Application` because it does no I/O of its own.

The tenant rides on the principal alongside the actor and the actor's roles (ADR 0028, as amended). The principal factory sets it, to the default tenant until a per-user tenant lookup arrives with tenant onboarding.

The write path fails closed. A command context in flight with no tenant set on the async flow throws `MissingTenantContextException` rather than stamping the default tenant. The command bus sets the tenant accessor in the same block as the command context, so a present context with an unset tenant is a dispatch-wiring regression, and the write path surfaces it rather than writing a silently-defaulted event. Off the command path (worker writes, the no-context fallback) the default tenant is the honest value and is stamped explicitly.

## Consequences

- Every tenant's data shares one set of tables. Isolation is a `tenant_id` predicate, so correctness depends on that predicate being present at every read, subscription, and projection. This is the discipline-dependent risk the model carries, recorded rather than hidden.
- The cross-tenant coverage mandate is the safeguard the model depends on. No query, command, subscription, or projection reaches production without a cross-tenant isolation test, enforced structurally so a registered type that lacks coverage fails the suite. The mandate is the model's load-bearing safety net, not an optional add-on.
- The default tenant is the absence of a tenant segment and the pinned `WellKnownTenants.Default` constant, so the legacy corpus and every new default-tenant stream resolve uniformly until a second tenant exists.

## The read-isolation enforcement mechanism

The enforcement is a per-store tenant predicate on every query-path read-model read, decided at P10.5 against the read-model connection shape on disk. Each query-path read resolves the current tenant from the accessor as its first action through one shared guard, throws when no tenant is set, and filters its query on the `tenant_id` discriminator. The guard centralizes the fail-closed throw in one place; the predicate lives in each read because the read-model stores share no query-composition seam to inject through.

Row-level security keyed on a per-connection session variable was the lean at acceptance and was examined first. Two facts on disk decided against it. The application connects to PostgreSQL as the schema owner, and a row-level-security policy does not constrain the owning role unless forced; forcing it would require a separate non-owner application role with its own grants and a second connection identity, an operational surface the system does not carry. And the read-model connection factory is shared by the projection write path, which has no tenant set until its own slice, so a connection-level policy would reach writes that must not yet be constrained and would break or silently filter projection work. A per-connection session variable does reset cleanly on pooled return under the shipped driver, pinned by an integration test, so row-level security stays available as a future defense-in-depth layer once a non-owner role exists; it is not the enforcement mechanism.

The predicate is not a per-author vigilance requirement. The cross-tenant coverage mandate is the safeguard that makes it production-grade: every query handler carries a cross-tenant test that seeds two tenants and asserts a read as one returns none of the other's rows, and the structural coverage harness fails the suite if a registered query type lacks that test, so a new query that ships without isolation coverage fails the build rather than slipping past review.

The read isolation enforced at P10.5 covers the query-path reads: the read-model store reads reached through the query bus, and the order-detail header read reached by the subscription-authorization endpoint, which sets the tenant from its principal the same way the bus does. The projection write path and its private lookups and the tenant-scoped SKU keys, owed to P10.6 when this section was first recorded, have since landed and are recorded next. The process-manager lookup reads landed at the process-manager propagation slice: the loop now resolves the tenant from the accessor, so those reads run under the loop's tenant. The user-roles read still does not carry a tenant and is enforced at the per-user-tenant slice; until that lands it resolves to the default tenant, the honest value while a single tenant exists.

P10.6 brings the projection write under the event's tenant. The current-tenant accessor is set from the event metadata at both projection dispatch boundaries: the in-process dispatcher sets it around the event-handler loop and restores it before the process-manager loop, and the replayer sets it around each replayed event, so a projection write and its private-lookup reads run under the tenant of the event that produced them. The process-manager propagation slice tenanted that loop too: the dispatcher now holds the tenant set across the process-manager loop rather than restoring it before, so the loop's reads and the process-manager metadata resolve the event's tenant from the accessor. Every projection unit of work tags the tenant on each insert and upsert but one, and the five projection-private lookup reads gain the tenant predicate, so a projection never resolves cross-aggregate identity across the tenant boundary. The exception is the order-id-to-payment-id mapping, whose `RecordAsync` inserts into a discriminator-carrying table without naming the tenant while its sibling SKU mapping tags through the accessor.

The projection write fails closed through the same resolve-or-throw guard the query path uses. After the set-point every projection write reaches its unit of work through a tenanted dispatch boundary, so an unset tenant is a dispatch-wiring regression the write surfaces rather than a silently-defaulted row. This narrows the Decision section's carve-out that off the command path worker writes stamp the default: the projection write now has a real tenant in hand from the set-point and is no longer the no-tenant-available worker write that carve-out described. The carve-out now covers only the writes that stay tenant-less: the outbox row, whose table carries no tenant column and whose consumer takes the tenant from the event metadata at the dispatcher's set-point, and the projection checkpoint, global by the decision migration 0017's header records.

The tenant-scoped SKU keys make the two SKU-keyed read models composite on the tenant and the sku together: the inventory-dashboard SKU uniqueness and the SKU-to-inventory-id primary key are keyed on the pair, so two tenants can each map the same sku, and the SKU write tags its tenant from the accessor like the other projection writes. The migration that swapped the global keys for the composite ones is safe on the all-default corpus with no rewrite, because every pre-existing row carries the default tenant and the composite key admits a single-tenant corpus unchanged. The SKU lookup read was the one asymmetry while the loop was untenanted: it was reached by process-manager handlers on that loop, so it took its tenant as an explicit parameter sourced from the causing event's metadata rather than from the accessor. The process-manager propagation slice closed the asymmetry: the loop is tenanted, so the read resolves the tenant from the accessor through the same fail-closed guard the write uses, and the lookup method signature, the seam the migration ran through, dropped the explicit `TenantId` parameter. The write and the read now take their tenant from the one accessor their shared loop tenant provides.
